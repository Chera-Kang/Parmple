# Parmple QA Test Case (TC) Design & Creation Rules

이 규칙은 팜플(Parmple) 프로젝트에서 기획서(Figma), Workflow 및 요구사항을 기반으로 **수동/자동화 테스트 케이스(TC)를 설계 및 생성**할 때 준수해야 하는 표준 거버넌스 헌장입니다.

---

## 1. 2-Track 문서 참조 및 우선순위 원칙 (Rule of Precedence)

기획서와 Workflow가 서로 다른 상태이거나 변경점 위주로 작성되어 있을 때, 아래 우선순위에 따라 통합 TC를 도출한다.

1. **전체 화면 흐름 및 순서 (Navigation / E2E)**:
   - `Workflow Figma`를 **진실의 원천(Single Source of Truth)**으로 삼는다.
   - 전체 사용자 여정(User Journey)과 메뉴/화면 간 이동은 Workflow의 순서를 기본 뼈대로 설계한다.
2. **세부 비즈니스 로직 및 유효성 (Validation / Negative)**:
   - `기획 Figma Description`을 **최우선(Override)**으로 적용한다.
   - 필수 입력값, 글자수 제한, 특수문자 허용 여부, 권한 제약, 에러 팝업 문구 등은 기획서 Description을 엄격히 반영한다.
3. **변경점(Change Log) 우선 반영**:
   - 기획 Figma 헤더/상단에 명시된 변경점(Patch)은 해당 화면의 기존 로직을 대체하며, 별도 언급이 없는 일반 동작은 Workflow의 표준 동작을 유지한다.

---

## 2. 테스트 케이스 4대 필수 계층 (Test Layer Coverage)

모든 기능/화면 단위 TC 생성 시 아래 4가지 유형이 반드시 균형 있게 포함되어야 한다. (Happy Path에만 치우친 얕은 TC 작성 금지)

| 분류 | 대상 및 목적 | 주 참조 소스 |
| :--- | :--- | :--- |
| **1. Happy Path (정상 흐름)** | 시스템의 주요 비즈니스 목적을 달성하는 표준 정상 흐름 | Workflow Figma |
| **2. Validation (입력값/경계값)** | 필수값 누락, 최대/최소 글자수, 형식 오류 등 필드별 유효성 검증 | 기획 Description |
| **3. Negative / Error (예외 처리)** | 권한 부족, 중복 데이터, 네트워크/서버 오류 시 에러 팝업 및 안내 문구 | 기획 Description |
| **4. E2E Scenario (연계 검증)** | 앞 단계에서 입력/선택한 데이터가 다음 단계 및 최종 목록에 정확히 반영되는지 검증 | Workflow + 기획서 |

---

## 3. 화면 식별 및 매핑 규칙 (Identifier Mapping)

- 기획서와 Workflow 간의 복잡한 Description 동기화 대신, **`화면 번호 / 화면명`**을 공통 식별자로 사용하여 1:1 매핑한다.
  - 예: `[14. 필터링 회신 관리]` ↔ `test_14_필터링회신관리.py`
- 기획서 프레임 타이틀이나 Workflow 노드 타이틀의 메뉴명을 기준으로 테스트 범위를 한정한다.

---

## 4. 표준 테스트 케이스(TC) 출력 포맷

TC 생성 시 아래 표준 마크다운/스프레드시트 구조를 준수하여 출력한다.

- **TC ID**: `TC-[기능번호]-[순번]` (예: `TC-14-001`)
- **테스트 분류**: `Happy Path` | `Validation` | `Negative` | `E2E`
- **테스트 명**: 검증 목적이 한눈에 드러나는 명확한 제목
- **사전 조건 (Pre-condition)**: 필요한 계정 권한(예: 제약사 담당자), 데이터 상태
- **테스트 절차 (Test Steps)**: 넘버링된 구체적인 사용자 행동 단계
- **테스트 데이터**: 입력에 사용할 구체적인 값/경계값
- **예상 결과 (Expected Result)**: UI에 표시되어야 할 구체적인 텍스트, 팝업 문구, 상태 변화 명시
- **중요도**: `High (P0)` | `Mid (P1)` | `Low (P2)`

## 5. 자동화(Playwright) 코드 및 Self-Healing 연계 표준

TC 설계 단계에서 작성된 데이터는 테스트 자동화 코드 구현 및 런타임 자가 치유(Self-Healing)의 직접적인 입력 소스가 되므로 다음을 엄격히 준수한다.

1. **구체적인 UI 텍스트 및 상태 명시 (Self-Healing 친화적 설계)**:
   - 예상 결과 작성 시 모호한 표현(예: "성공 메시지가 뜬다", "에러가 표시된다")을 절대 금지한다.
   - 실제 UI에 노출되는 정확한 텍스트(예: `"회신이 완료되었습니다." 알럿 노출`, `"사업자등록번호 10자리를 정확히 입력해주세요." 경고 문구`)를 명시한다.
   - 이는 프론트엔드 UI 변경으로 기존 셀렉터가 깨졌을 때, `automation/web/playwright/self_healing` 파이프라인이 에러 화면의 DOM/스크린샷(`error_artifacts`)에서 정확한 대체 Locator를 자동 탐색/복구하는 핵심 기준이 된다.
2. **복잡한 UI 위젯 식별**:
   - AG Grid 테이블, Radix UI 다이얼로그 모달, 커스텀 드롭다운 등은 테스트 절차에 위젯 유형을 명시하여 셀렉터 오작동을 방지한다.
3. **자동화 스크립트 작성 시 거버넌스 헌장 준수**:
   - 생성된 TC를 바탕으로 `automation/web/playwright/testcase/test_*.py` 스크립트를 작성할 때는 반드시 [qa_automation.md](file:///c:/Dev/Parmple/.agents/rules/qa_automation.md)의 **Zero False-Positive(상태 변화 단언 필수)** 및 **셀렉터 표준**을 100% 준수하여 코드를 생성해야 한다.

## 6. 점진적 3단계 TC 생성 및 확장 전략 (3-Phase Progressive Strategy)

테스트 자동화의 신속한 전체 커버리지 확보, 세부 방어 로직의 정밀도, 그리고 실무 비즈니스 Workflow의 완결성을 위해 아래 3단계 전략을 엄수한다.

1. **Phase 1: 코어 베이스라인 우선 구축 (Core Smoke Baseline)**:
   - 기획서가 부재하거나 신규 화면/도메인 최초 생성 시에는 **기능당 5~6개의 핵심 시나리오**를 우선 생성한다.
   - 포함 범위: 화면 진입/헤딩 확인, 탭/AG Grid 필수 컬럼 렌더링, 대표 필수값 방어(`disabled` 또는 페이지 유지), 대표 미선택 액션 방어, 검색/초기화.
   - 목적: 서비스 전 메뉴의 기본 안전망(Smoke Net)을 신속히 확보하고 "100% Pass" 가능한 견고한 토대를 마련한다.

2. **Phase 2: 코어 기반 심화 및 원자 단위 유효성 확장 (Atomic Validation & Boundary Deep-Dive)**:
   - 이미 1차 코어 TC가 완성된 기능에 대해 입력 폼의 세부 방어 로직을 정밀 검증한다.
   - 확장 방식:
     - **원자화 분리 (Atomic Split)**: 하나의 함수에 묶인 다중 검증을 1:1 독립 테스트 함수로 분리.
     - **필드별 경계값 심화 (Boundary Deep-Dive)**: 입력 필드별 최대/최소 글자수, 공백, 특수문자, 날짜 포맷, 형식 오류(예: 사업자등록번호 형식) 등 상세 밸리데이션 추가.
     - **예외/방어 심화 (Negative Deep-Dive)**: 비정상 데이터 입력 후 버튼 비활성화 유지 또는 오류 툴팁/경고 문구 가시성 단언.
   - **프롬프트 품질 원칙**: 심화 확장 시 한 번에 모든 조건을 섞어 요청하기보다, '특정 폼의 필드별 유효성' 또는 '예외 케이스'처럼 목적별로 집중 요청할 때 AI의 정밀도와 단언문 완성도가 극대화된다.

3. **Phase 3: 실제 동작 비즈니스 E2E 및 자가 치유 실행 (Dynamic E2E Workflow & Self-Healing Action)**:
   - 화면 렌더링과 유효성 검증을 넘어, **실제 데이터를 입력/생성하고 비즈니스 흐름에 따른 상태 변화(State Mutation)를 끝까지 추적·검증**한다.
   - 포함 범위:
     - **실제 폼 데이터 작성 및 등록/발송**: 모달/페이지에서 필수 데이터를 채우고 실제 '작성하기/등록/발송' 버튼을 클릭하여 데이터 생성.
     - **목록 및 상태 단언 (CRUD Lifecycle)**: 방금 생성된 고유 식별 데이터(예: 타임스탬프 기반 계약명/업체명)가 목록 그리드에 1건 추가되었는지 실제 단언.
     - **크로스 계정(Cross-Account) 연계 수신 검증**: 발신자 계정(CSO)에서 보낸 데이터가 수신자 계정(제약사 또는 하위 CSO)에 로그인했을 때 '수신함/받은 목록'에 정확히 도착했는지 체인 검증.
     - **Self-Healing 연계**: 실제 런타임 플로우 중 발생한 예기치 않은 모달, 오버레이, 셀렉터 변경점은 Self-Healing 파이프라인과 결합하여 실시간으로 탐지/보정하여 완결.

## 7. Figma / Workflow (기획서·화면정의서) 기반 통합 TC 도출 전략 (Figma-Driven Integrated Strategy)

기획서, Workflow(사용자 여정 맵) 및 Figma 화면 정의가 명확히 존재하는 경우, 기존의 '점진적 3단계(스모크 ➔ 유효성 ➔ 비즈니스)' 방식 대신 **Figma 워크플로우와 화면 사양을 직접 매핑하는 단일 통합 생성 기법(Spec-Integrated Single-Pass Generation)**을 적용한다.

### 1) 3단계 방식 vs Figma 기반 기법 비교

| 비교 항목 | 기존 점진적 3단계 전략 (3-Phase) | Figma / Workflow 기반 전략 (Figma-Driven) |
| :--- | :--- | :--- |
| **적용 상황** | 기획서/사양이 없거나 미완성인 도메인 | Figma Workflow(여정 맵) + 화면 Description이 존재할 때 |
| **생성 순서** | Phase 1(스모크) ➔ Phase 2(유효성) ➔ Phase 3(E2E) | Workflow 노드/엣지 트래버스 기반 단일 통합 TC 도출 |
| **E2E 흐름 설계** | 3단계에 이르러서야 E2E 체인 형성 | Workflow 노드 간 이동 경로가 Day-1부터 E2E 뼈대로 바로 활용됨 |
| **검증 도출 소스** | 기본 화면 탐색 및 경험적 방어 로직 | Workflow Edge (흐름/분기) + Frame Description (단언 텍스트/경계값) |
| **데이터 연속성** | 단일 화면 위주의 독립 검증 중심 | 앞 노드 입력값 ➔ 뒤 노드 프로필/목록 1:1 매핑 단언 (Data Lineage) |

### 2) Figma Workflow 기반 TC 추출 4대 핵심 구조

1. **사용자 여정 노드/엣지 매핑 (Node & Edge Journey Mapping)**:
   - Figma Workflow의 각 노드(화면/모달)와 엣지(버튼 클릭/분기)를 1:1 테스트 단계로 변환한다.
   - 예: `[로그인]` ➔ `[회원가입 진입]` ➔ `[사업자/신고번호 검증]` ➔ `[계정 정보 및 약관]` ➔ `[승인 대기]` ➔ `[프로필(내 정보/업체 정보)]`
2. **화면 Frame Specs / Description 결합 단언 (Frame Description Assertion)**:
   - 각 노드 화면의 Figma Description 및 필드 레이블 사양에서 단언(Assertion) 기준을 도출한다.
   - 예: 비밀번호 규칙(`6자 이상, 영문+숫자+특수문자`), 사업자번호 형식(`-없이 숫자만`), 신고번호 주의사항(`제, 호 제외, - 포함`), 서류 파일 확장자(`pdf, png, jpg, jpeg 최대 10MB`).
3. **분기 노드(Decision Node) 조건별 케이스 분리**:
   - Workflow 상의 조건 분기점(Decision Diamond)마다 독립된 시나리오 TC를 생성한다.
     - Case A: **기존 등록 사업자** ➔ 의약품 판촉영업 신고번호 입력 모달 진입
     - Case B: **신규 사업자** ➔ 사업자등록증 및 판촉영업 신고증 파일 업로드 폼 진입
4. **상태 전이 및 데이터 연속성 단언 (Cross-Node Data Lineage)**:
    - 가입 시 입력한 대표자명, 업체명, 사업자번호가 가입 완료 후 `프로필(내 정보/업체 정보)` 페이지에 1:1 완벽 반영되는지 화면 간 연속성을 검증한다.
    - 프로필 페이지 내 2차 액션(CSO 교육 수료증 등록, 도장 이미지 등록)까지 단일 E2E 라이프사이클로 연결한다.

### 3) 피그마 하위 인터랙션 완전 탐색 (Full Drill-Down) 및 모듈화 원칙

1. **도착점(Landing Page) 종결 금지 및 하위 탐색 필수 (Never Stop at Destination)**:
   - 워크플로우 상의 최종 목적지 화면(예: 프로필/내 정보)에 도달했다고 해서 테스트를 종료해서는 안 된다.
   - 해당 화면에 설계된 **모든 드롭다운 메뉴, 팝업/모달, 서브 섹션, 연결된 서브 페이지(Sub-page)**까지 100% 완전 탐색(Drill-down)하여 검증해야 한다.
2. **1-Subflow 1-Test Function 원칙 (스파게티 E2E 방지)**:
   - 전체 여정을 하나의 거대한 단일 함수(`test_e2e_all`)에 모두 넣지 않는다.
   - **기본 여정(Happy Path)**과 **각 기능 영역별 서브플로우(예: 계정 관리 모달군, 업체 관리 모달군, 독립 서브페이지)**를 독립된 `def test_...` 함수로 개별 분리하여, 테스트 실패 시 어느 기능에서 문제가 발생했는지 즉각 식별하고 병렬 실행/선택 실행이 가능하도록 한다.
3. **모달(Modal) vs 독립 페이지(Page) 구분 처리**:
   - 단순 레이어 오버레이(Modal/Dialog)는 `div[role='dialog']` 범위 내에서 단언하고 닫기/취소 후 복귀를 검증한다.
   - URL이 전환되는 독립 서브 페이지(Page)는 `expect(page).to_have_url(...)` 및 고유 `h2` 헤딩, LNB, 테이블을 검증하고 원래 메인으로 복귀하는 네비게이션까지 완결한다.

### 4) Figma Description & Naming Tag 파싱 규칙

1. **프레임 네이밍 접두어 태그 (Naming Convention)**:
   - `[모달]`, `[팝업]`, `[얼랏]`: Playwright의 `role='dialog'` 또는 `role='alertdialog'`로 매핑.
   - `[페이지]`, `[SubPage]`: 페이지 전체 전환으로 인식하여 URL 및 LNB/Header 전체를 단언.
2. **Description 텍스트의 테스트 단언 강제 (Description-to-Assertion)**:
   - 피그마 프레임 옆에 적힌 `description`은 단순 참고용 메모가 아니라 **"반드시 자동화 코드로 검증해야 하는 인수 조건(Acceptance Criteria)"**으로 취급한다.
   - 예: `이름 : 테스트_mmdd-hhmm` ➔ 실제 시간 동적 생성 후 fill 단언
   - 예: `회원탈퇴는 진행하지 않고 팝업 발생 여부만 확인` ➔ 팝업 노출 단언 후 `[취소]` 클릭
   - 예: `현재와 같은 비밀번호로 변경` ➔ 비밀번호 입력 필드 검증 후 닫기

### 5) 제로-노력(Zero-Effort) AI 자동 발동 규칙 (Autonomous Execution Contract)

> **핵심 원칙**: 사용자가 복잡한 골든 프롬프트를 매번 기억하거나 길게 작성할 필요가 없다.  
> 사용자가 단지 **"Figma URL"**을 제시하거나 **"피그마 기반으로 TC 작성해줘"**라고만 짧게 요청하더라도, AI 에이전트는 아래 4대 규칙을 **기본 동작(Default Behavior)**으로 무조건 자동 강제 수행해야 한다.

1. **자동 완전 탐색 (Auto Drill-Down)**:
   - 사용자가 "A > B 흐름 작성해줘"라고만 해도, 목적지 화면(B)에 도달해서 멈추지 않고, B 화면에 딸린 **모든 드롭다운 메뉴, 팝업/모달, 연결된 서브페이지까지 스스로 추적하여 100% 테스트 범위에 포함**한다.
2. **자동 1-Subflow 1-TC 분리 (Auto Modularization)**:
   - 사용자가 분리하라고 말하지 않아도, 메인 여정과 각 서브 기능군을 독립된 `test_...` 함수로 개별 분리하여 스파게티 E2E를 원천 차단한다.
3. **자동 Description 파싱 및 단언문 강제 (Auto Description-to-Assertion)**:
   - 피그마의 `description`과 Bent Connector(화살표) 라벨을 자동으로 파싱하여 유효성 포맷, 경고 팝업 확인, 버튼 비활성화 등의 단언문을 테스트 코드에 빠짐없이 삽입한다.
4. **자동 실행 및 자가 검증 (Auto Self-Verification)**:
   - 테스트 코드를 작성한 후 질문으로 멈추지 않고, 즉시 `run.py`를 실행하여 100% Pass를 스스로 검증한 뒤 최종 리포트와 함께 결과를 사용자에게 보고한다.

따라서 사용자는 아래와 같이 **한 줄짜리 자연어**만 입력해도 동일한 고품질 결과를 얻을 수 있다:
```markdown
"https://www.figma.com/... 이 피그마 URL의 {섹션명} 보고 자동화 TC 작성해줘"
```
